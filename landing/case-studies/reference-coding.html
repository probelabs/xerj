THE SAME CLAUDE CODE.
A FRACTION OF THE TOKENS.

When an agent meets an API it does not know, it guesses, fails, and guesses again — each lap burning the expensive kind of token. We measured whether handing that same Claude Code a XERJ-retrieved reference changes the outcome. It does: on code the model has not memorised, retrieval makes the model correct where memory fails outright — 15/15 vs 1/15 — at 1.5–2.7× fewer output tokens than native Claude Code grepping the source itself, across five languages. And where the model already knows the code, retrieval is honest overhead — which we also measured, and say plainly.

THE MEMORISATION WALL

  • Unknown API → retry loops. Faced with a library it cannot recall, the model invents method names, fails to compile, and loops — spending output tokens, the 5×-priced kind, on every lap.
  • grep is not free either. Native Claude Code can search the source, but that pulls files into context (on one corpus, 1.06M input tokens) and costs agent turns.
  • A compiler leaks names, never contracts. `rustc`'s "did you mean" can recover a method name — at 20–25× the tokens — but never a runtime rule like "seal before you read".

THE XERJ ANSWER

  • Index the references once. Point xerj autoindex at the libraries that already solved the problem; retrieval is O(1) regardless of tree size.
  • Retrieve, then write. The exact definition — with the contract in its doc — lands in the prompt. The model reads a passage instead of re-deriving an algorithm.
  • Same agent, fewer laps. The retrieval replaces the grep and the guessing: correct on the first shot, at a fraction of native Claude Code's tokens.

THE SAME TASK, TWO WAYS.

One Java task: build an append-only ledger that must be sealed before it can be replayed, truncated to a checkpoint. bare cannot read the library, so it reinvents the whole thing — 503 lines — and still fails the seal contract. XERJ, handed the reference, writes it in four lines and cites the rule it learned:

bare · 503 LINES · ~36,000 OUTPUT TOKENS · STILL FAILED
// reinvented an entire append-log + checkpoint + seal state machine from
// memory, guessing the API surface … 503 lines … wrong truncation semantics
// → hidden test FAILED.
XERJ · 4 LINES · 103 OUTPUT TOKENS · PASSED
public static Ledger upTo(long[] vals, long seq) {
    Ledger l = Ledger.open();
    for (long v : vals) l.append(v);
    l.checkpoint(seq);   // keep 0..seq
    l.seal();            // required before replay
    return l;
}

WHAT WE WON'T OVERCLAIM.

01
ON MEMORISED CODE, RETRIEVAL IS OVERHEAD.
On popular public code the model has trained on — even a 256-value quantization table it reproduces from memory — bare is cheapest, and injecting a large reference can be the worst arm. Reference-coding's value is gated by memorization; it pays on your private, proprietary, or unfamiliar code, not on library references the model already knows.
02
THE WIN IS MEASURED ON SYNTHETIC LIBRARIES.
The unfamiliar corpus is 13 libraries written for this study — unfamiliar by construction, so the model cannot bluff. A genuinely large private codebase is the honest end-state we have not yet measured; the native-vs-XERJ gap should grow there, because grep cost scales with the tree while retrieval stays flat.
03
WE TRIED TO IMPROVE THE SERVER AND IT DIDN'T HELP — YET.
We enriched XERJ's index (richer symbols + identifier sub-word splitting) and measured it against the old server on the same corpus. On realistic queries it did not improve ranking, because the reference libraries carry enough prose for lexical BM25 to already saturate. The robust win is retrieval-vs-none, which both server versions deliver equally. Full scorecard published.
